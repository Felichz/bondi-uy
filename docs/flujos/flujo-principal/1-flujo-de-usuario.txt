Main flow:

Alright, here I'm going to describe the user flow from start to finish. The first part is already quite advanced: the user enters a origin address and a destination address, then presses the search button, and the app shows the user a carousel of travel options. There, the user can see the preview of the trip recommended by the app and can directly press the button to start the trip on that recommended route, or, if the user is more demanding, can use the carousel to browse the different options the app offers. While the user moves through the carousel, the map shows a preview of the trip focused on the carousel and centers the camera zoom, so the user can see it. Also, if the option has an ETA for the first stop, that is, the first bus leg, then the preview can show the bus in real time and a green segment drawn from the bus to the stop where the user would have to get on.

Then, when the user presses the button to start the trip and selects an option, we enter the active trip phase. Polling of the real-time bus starts. If there is an ETA, the map camera focuses on the trip, and we start a trip assisted step by step. First comes the walk to the stop where the user has to get on. Here we keep recording the user's location and draw a blue segment from the user's location to the stop. A widget shows the information of the current step, showing the distance the user is currently at and possibly a small progress circle next to the distance so the progress of the walk can be seen. That progress is calculated from the initial distance the user was at and the current distance. We always have the current distance because the blue segment drawn on the map updates automatically according to the user's location, maybe with a timer, for example every 5 seconds, where the optimal walking segment between the current location and the stop is calculated. So the distance indicator is always updated at the same time, because it represents the distance of that current segment. Also, the approximate remaining time walking to the destination, similar to Google Maps.

Then, when the user reaches the stop, the travel assistant, that is, the app or the UI, automatically moves to the next step of the trip, which is waiting for the next bus. If there is no ETA, the user is shown which line to wait for, and the map simply focuses on the stop. If there is an ETA, the map focuses on the stop and also on the real-time bus that is on its way, so the user can see how long until their bus arrives. Also, in this step the map adjusts the zoom every time a new update of the bus coordinates arrives, because the focus must always stay between the stop and the bus that is on its way. Then, here the logic is the same: we keep monitoring the user's location with the same 5-second timer, but in this phase what we do is check whether the user has started moving along the bus leg that goes from the origin stop to the destination stop. This logic is the same whether there is an ETA or not. The only difference is that when there is an ETA, the map always renders the bus icon using the coordinates from this bus waiting step. But when we detect that the user has got on the bus, we stop the real-time bus polling, because now the user's location becomes the source of information we use to draw the bus location. So in this case those bus coordinates no longer matter. Now we show the user the bus icon at the user's location, and the map adjusts the focus based only on the destination stop and the user's location, that is, the bus drawn at the user's location. Then, when the app detects that the user has reached the destination stop, the app automatically moves to the next step, where the map draws the user's location again in the default way (because they are back in walking mode, no longer on a bus). This next step can again be waiting for a bus, and the case is identical to the one explained before. Here the ETA polling for this new stop starts, and if a real-time bus is detected, the map shows it and adjusts the zoom, as we described before. The logic should be the same and should be reused. If not, this next step is a walk again, to walk to another stop, and here we also reuse the entire same flow as before for the first walk-to-stop step. Or it may be the last walk step, to the destination point. In that case the flow is also identical to a walk to a stop. The only difference is that instead of a stop, the target is the destination point. When we detect that the user has reached the destination point, the trip ends automatically.
