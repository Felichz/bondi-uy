=======

Tu rol principal es implementar funcionalidades para la aplicación Flutter BondiUY, enfocándote en una separación limpia entre una capa de UI puramente presentacional y una capa de lógica de negocio.

**Principios Arquitectónicos Fundamentales:**
*   **Separación Estricta de Responsabilidades:** La UI es para la presentación; la Lógica es para las reglas de negocio y el procesamiento de datos.
*   **Visión de la UI:** La capa de UI es el "manifiesto de la visión del creador de la app", como se detalla en `lib/2-ux_philosophy.md`. Esta visión restringe estrictamente las posibilidades para alinearse con los flujos de usuario y la visión de la app. No permitas nada desalineado con esta visión.
*   **Minimalismo Radical:** "Menos es Más". Muestra solo información y opciones esenciales. Evita la sobrecarga visual y de opciones. Cada elemento en pantalla debe tener un propósito claro.
*   **Filosofía UX "Abuelita First":** Diseña para una simplicidad e intuición radicales. Las acciones deben ser obvias y el lenguaje claro, sin jerga técnica.

**Capa de UI: Responsabilidades y Restricciones:**
*   Completamente agnóstica a la lógica de negocio.
*   Maneja toda la lógica presentacional: estilos visuales, estados de componentes internos (ej: expandido/colapsado que no afecten el estado global de la app más allá de la presentación inmediata), animaciones, interacciones del usuario y formateo de datos para visualización (ej: convertir segundos a "X min").
*   Define una API mínima, abstracta y estricta para la capa de Lógica (ej: `AppUiState` como entrada, y la invocación de acciones/callbacks expuestos por la capa de lógica como salida). Este es el *único* punto de contacto.
*   **Mapbox es una responsabilidad de la UI.** Esto incluye la gestión directa de la cámara del mapa (zoom, paneo, seguimiento), la administración de capas y fuentes de datos de Mapbox, el renderizado de geometrías (puntos, líneas, polígonos), la personalización de estilos y la gestión de gestos e interacciones directas con el mapa. La capa de Lógica proveerá datos geoespaciales (coordenadas, GeoJSON) pero no directivas específicas de Mapbox.
*   Recibe datos pre-procesados de la capa de Lógica, listos para mostrar.
*   Maneja estado específico de la UI que es puramente presentacional o de navegación dentro de la UI (ej: `indiceTramoActual` para la navegación del viaje). Si la modificación de este estado local por la UI (ej: el usuario navega al siguiente tramo) requiere nuevos datos o una acción de la capa de Lógica (ej: obtener detalles actualizados para ese nuevo tramo), la UI será responsable de invocar la acción correspondiente en la capa de Lógica.
*   No debe permitir que ninguna funcionalidad o dato impacte la UI sin pasar por su contrato definido.
*   Renderiza eficientemente; evita re-renderizados completos innecesarios de la UI si solo cambian partes.

**Capa de Lógica: Responsabilidades y Restricciones:**
*   Maneja toda la lógica de negocio: obtención de datos de servicios externos (ej: OTP, geocodificación), procesamiento de datos, cálculos y la determinación del estado de la aplicación.
*   Prepara los datos en un formato limpio y agnóstico a la UI para la capa de UI (contenido en `AppUiState`).
*   *No* debe tener conocimiento de detalles de implementación específicos de la UI (ej: widgets de Flutter, Mapbox, colores, fuentes).
*   Su único propósito es servir a la capa de UI proporcionando el `AppUiState` y manejando las acciones invocadas por la UI. Es un "chef de datos".
*   No proporciona texto presentacional (ej: envía números para duración/distancia; la UI lo formatea). Esto también facilita la internacionalización (I18N) y localización (L10N), que son manejadas exclusivamente por la capa de UI. Las constantes string para tipos de advertencia están bien (la UI decide cómo y con qué texto mostrar cada caso).

**Protocolo de Comunicación (UI <-> Lógica):**
*   La UI observa/recibe el estado (`AppUiState` o similar) de la capa de Lógica.
*   La UI invoca acciones/callbacks (expuestos por la capa de Lógica) en respuesta a eventos del usuario.
*   La comunicación debe ser mínima y estrictamente definida por este contrato.
*   La capa de Lógica comunica errores o estados excepcionales a la UI a través de campos dedicados en `AppUiState` (ej: `mensajeErrorGlobal`, `estadoCalculoRuta` indicando `ERROR`). La UI es responsable de interpretar estos estados y presentar la información de error apropiada al usuario.

**Flujo de Trabajo y Comportamiento de Desarrollo:**
*   **Consulta el Código Antiguo:** La versión anterior del proyecto (`old/`) contiene soluciones funcionales para muchos detalles de implementación ("cómo hacer" con Mapbox, APIs, procesamiento de datos, etc.). Úsalo extensivamente como referencia para evitar resolver problemas ya solucionados. Esto es especialmente cierto para interacciones complejas de UI o visualizaciones de datos específicas que ya funcionaban bien en la versión anterior. El objetivo del refactor es la mejora arquitectónica y la separación de capas, no la reinvención de funcionalidades ya probadas.
*   **Comprende la Intención Original:** Al refactorizar o implementar, es crucial que comprendas la intención y el comportamiento de los componentes y funcionalidades originales. Intenta mantener esa experiencia de usuario, adaptándola a la nueva arquitectura, a menos que se indique explícitamente un cambio (como el carrusel de selección de rutas).
*   **Toma de Decisiones:** Para decisiones significativas que afecten el flujo de usuario, la UX o el diseño central, debes consultarme (actuando como PM). Los detalles menores de implementación que no alteren la UX o la arquitectura pueden decidirse autónomamente.
*   **Calidad del Código:** Aspira siempre a un código robusto, limpio, elegante, bien estructurado y profesional.
*   **Aserciones:** Al generar código, incluye proactivamente aserciones relevantes donde sea apropiado para validar contratos de datos, precondiciones o postcondiciones, especialmente en los límites entre capas o componentes críticos. Es aceptable que la aplicación falle en desarrollo si una aserción no se cumple, ya que ayuda a identificar problemas temprano.
*   **No Delegar Concerns de UI a la Lógica:** La capa de UI es responsable de su propia lógica presentacional. La capa de lógica es un procesador de información al servicio de la UI; no debe contener lógica de presentación.
*   **Adherencia Proactiva a Principios:** Cuando te solicite implementar una funcionalidad o realizar cambios, evalúa proactivamente cómo la solicitud se alinea con estos principios arquitectónicos y de UX. Si identificas un posible conflicto o una forma de adherirse mejor a la visión, por favor, señálalo y sugiere alternativas antes de proceder con la implementación directa.

**Contexto Específico de Funcionalidades de la App (Ejemplos para guiar el pensamiento):**
*   **Estados del Mapa y Fases de la App:** La UI debe reaccionar a diferentes fases de la app (`FaseApp`), mostrando en el mapa solo lo relevante para cada fase (ej: paradas en fase inicial; previsualización de rutas y paradas del itinerario en fase de opciones; ruta activa y actualizaciones en tiempo real en fase de viaje en curso).
*   **Opciones de Ruta:** Al mostrar opciones de ruta, la UI debe permitir la previsualización de cada una en el mapa, destacando la recomendada. La navegación entre opciones es un concern de la UI.
*   **Viaje Activo:** Durante un viaje activo, la UI es responsable de mostrar el progreso, permitir la navegación entre tramos (ej. caminar, esperar, bus), y comunicar a la capa de lógica qué información en tiempo real podría ser necesaria (ej. para qué tramo de bus específico).
*   **Interacción con Paradas:** Cuando el usuario selecciona una parada en el mapa, la UI solicita a la capa de lógica la información relevante (ETAs, líneas). La presentación de esta información en un panel es responsabilidad de la UI.
